* pilish: session management design

Design decisions for extending the =pilish= layer with Emacs <-> pi
session management.  Recorded during a grilling session on 2026-08-09.  This
document captures the agreed design; the layer README describes implemented
behavior.

** Context

The layer currently wraps the MELPA =pilish= frontend (RPC-backed
chat/input buffers) and adds a purpose window layout, launch-directory
resolution, and leader keybindings.  The package itself already provides
per-project sessions, named parallel sessions, a transient menu (new/resume/
fork/name/model), and per-directory session resumption.

The goal: a session management solution where each opened pi session behaves
like a project — a workspace with its own buffer set, restorable across
closes and restarts.

** Decisions

*** D1. Workspace mechanism: persp-mode (spacemacs-layouts)

Enable the =spacemacs-layouts= layer (persp-mode + eyebrowse).  One
perspective per opened pi session.  Rejected: project.el (keys by directory,
cannot express parallel sessions in one dir) and a custom buffer registry
(reimplements persp-mode).

*** D2. Session list UI: unified live/closed picker, framework-agnostic

One list model shared by every session picker (=switch-session=,
=switch-session-in-dir=, =start-new-session=, =close-session=,
=delete-session=):

1. A single builder (=pilish//session-targets=) returns
   (LIVE . CLOSED) candidate alists.  LIVE = active pi chat buffers
   (the ground truth, see D3), most recently used first; CLOSED =
   files on disk not loaded by an active buffer.  Each candidate maps
   to a target plist the caller dispatches on (:buffer for live,
   :entry for closed).
2. Rendering is one shared picker (=pilish//pick-session=):
   under helm the groups are separate sources ("Live sessions" /
   "Closed sessions" — real section headers); otherwise
   completing-read with non-selectable header rows
   (=────── Live sessions ──────=) between the groups, affixation
   (status glyph ●/○, message count, age), pre-sorted order (live
   first) preserved via display-sort-function identity.  Selecting a
   header row re-prompts.  This works under helm-mode, ivy, vertico
   and the plain minibuffer.
3. Some commands list only one group: close-session offers live
   sessions only (its default is the current perspective's session);
   switch lists both; delete lists both.

(2026 update: previously the switch list derived "opened" from the
persp mapping and had no group boundary; the close/delete picker had
helm sections but no completing-read boundary.  Both are now the
shared model above.  Second 2026 update (D16): the switch list's
sections are generalized from two hardcoded groups to an ordered
(NAME . ALIST) list — a per-remote-host section slots in between the
local live and closed groups; the other pickers still use the classic
two groups.)

*** D3. Session identity and perspective mapping

- Registry alist =persp-name -> session-file= (+ =label-locked= flag),
  persisted to the cache directory (=spacemacs-cache-directory=), updated on
  perspective create/rename/destroy, saved on Emacs exit (atomic writes:
  temp file + rename).
- =live= <-> an active pi chat buffer exists (mode
  =pilish-chat-mode= with a live process).  Liveness is
  always read from the chat buffers (=active-chat-buffers=), never
  from the registry or the perspective mapping — those can be stale
  (a killed perspective still registered) or miss sessions started
  outside the registry flow.  A perspective with a dead pi process
  lists as closed; switching to it revives the process (the registry
  still maps the perspective).
- After an Emacs restart everything is closed unless auto-resume is enabled
  (see D8).

*** D4. Perspective naming and label sync

- Format: =«title» · «abbrev-path»= (abbreviated full cwd from JSONL header).
- Title: session =/name= (session_info) -> first-message snippet (~40 chars)
  -> =New session= placeholder (before the first prompt).
- Exact collisions (same title + same dir) get a short-uuid suffix.
- Sync policy: auto-sync the title part when the session is renamed — advice
  on =pilish-set-session-name= (immediate) plus lazy compare-and-
  rename on the next session-list scan (=/name= slash command path).  A
  perspective renamed by the user (=persp-rename=, SPC l r) sets
  =label-locked= and stops auto-sync.

*** D5. Buffer attribution and common buffers

- persp-mode ='free= attribution (Spacemacs default) attaches every new
  buffer (files, terminals, pi chat/input) to the current perspective.
- Common buffers (=*scratch*=, =*Messages*= by default; defcustom regexp
  list) are injected into every perspective via =persp-created-functions=.
  Injection, not filtering: persp's =persp-common-buffer-filter-functions=
  is an exclusion mechanism (filtered buffers belong to no perspective and
  vanish from the restricted buffer list).  Injected buffers are in all
  perspectives, so they appear in =SPC b b= and are killable without
  foreign-buffer prompts.
- =SPC b B= (non-restricted list) remains the escape hatch.

*** D6. Open/switch state machine

Closed -> open (selecting a closed session):
1. Create the perspective (named per D4) and switch to it.
2. =pilish//open-session-file-with-name= (the layer's mirror of
   =pilish-open-session-file=): setup chat/input buffers, start
   the process, resume the exact session file — under a launch name that
   guarantees fresh buffers (see same-dir collision below).
3. Replay the registry's captured buffer specs through persp's load
   dispatch (see D7).
4. Apply the pi window layout, passing the session's own chat/input
   buffers explicitly; focus the pi input buffer.  (The layout fallback
   must not pick the most-recent pi-chat buffer from another
   perspective.)

Live -> switch (selecting a live session):
1. =pilish//switch-to-live-buffer=: =persp-switch= to the
   perspective owning the active chat buffer (Spacemacs restores its
   window configuration).  A live buffer outside any perspective falls
   back to =pilish//adopt-live-buffer=, which registers the
   existing buffers/process into a fresh perspective — no second
   process is spawned.

Closed -> switch (reviving a registered perspective): picking a
closed session still routes through =pilish//open-or-switch=,
which prefers the perspective the registry (or
=live-session-mappings=) still maps for the file — the session's
perspective exists but its process died.  =switch-to-session= then:
1. =persp-switch= to the perspective (Spacemacs restores its window
   configuration).
2. If the pi process is dead: revive silently (=setup-session= + resume of
   the registry's session file).
3. If the process is alive but its loaded session file (from =get_state=)
   differs from the registry's file — the chat buffer is shared by every
   unnamed session of its directory, so another perspective may have
   resumed a different session into the same process, or a transition was
   skipped while the process was busy — re-resume the registry's file.
4. If the perspective displays a chat buffer of a *different* directory
   (drifted in through the layout's most-recent-buffer fallback), re-assert
   the pi layout with the correct chat/input buffers.

Same-dir collision behavior: reopening a closed session never reuses the
directory's live unnamed chat buffer/process.  Named sessions reopen under
their recorded name; unnamed sessions open as the directory's canonical
session when no live unnamed session exists, and otherwise under a generated
name (title + session-file uuid prefix) so the reopened session runs
side-by-side with its own buffers and process.  The package still allows one
*unnamed* chat buffer per directory; the generated name makes the reopened
session a named one.

=pilish/switch-session= excludes the session of the current
perspective (you are already in it).

*** D7. Buffer save/restore: persp's public dispatch, no duplication

- pi layer registers chat/input handlers only, at the front of persp's
  public defcustoms:
  - =persp-save-buffer-functions=: chat/input buffers ->
    =(def-buffer-pi-chat name dir launch-name session-file)= (dir/launch-name
    from the buffer's session identity, session-file from
    =pilish--state=); nil for everything else.
  - =persp-load-buffer-functions=: restore = =pilish--setup-session=
    + resume (open-session-file minus window display).
- Registry buffer specs are captured by running persp's save dispatch over
  the perspective's buffers (each owner classifies its own: files/dired by
  persp defaults, terminals by my-persp if present, chat/input by pi) — on
  close-session (before killing), perspective switch-away, and Emacs exit.
- Reopen replays the specs through persp's load dispatch.  No per-type
  classify/restore logic lives in the pi layer.
- No /proc/<pid>/cwd in the pi layer: that is vterm-only logic, owned by
  my-persp.

*** D8. Restart behavior: user's choice, documented

- Auto-resume off (current default): after a restart all sessions are
  closed; the manager list reopens them (registry restores buffers).
- Auto-resume on (=dotspacemacs-auto-resume-layouts t=): persp restores
  perspectives with files (persp defaults), terminals (my-persp), and pi
  sessions (pi layer's chat/input load handler — process restarted, session
  file resumed).  Caveat: N sessions = N pi processes at startup.
- Both modes documented in the README.

*** D9. Close/delete session

Two commands sharing one teardown core (=pilish//close-session-
in-persp=): =pilish/close-session= (SPC a i d) and
=pilish/delete-session= (SPC a i D):

1. Target selection: the pickers list LIVE pi chat buffers (active
   processes) — the perspective containing the chosen buffer is
   resolved only when the selection is acted on.  Close uses the
   current perspective's session without prompting (listing only when
   it has none); delete always prompts and additionally offers closed
   sessions (files on disk not loaded by an active buffer).  Both use
   the unified picker (D2): live first, section boundary, annotated
   candidates.  The picker's default is the current perspective's
   session, resolved from its active chat buffer; when there is no
   active buffer it falls back to the registered session (registry
   entry or chat buffer), so the default still resolves for
   dead-process perspectives.  Under helm the default must be passed
   as =:preselect= (a quoted regexp), not =:default=: =:default= only
   fills the minibuffer for =next-history-element= and left the
   cursor on the first candidate, so the delete picker never opened
   on the current session.
2. Capture buffer specs (D7) — close only.
3. Kill the pi process (only when the perspective owns its chat
   buffer; a shared same-directory chat buffer is spared), then the
   perspective's buffers (files, terminals, chat/input) — standard
   per-buffer unsaved-change prompts; common buffers and other
   perspectives' buffers never touched.
4. Kill the perspective, then switch to the next perspective (persp
   display order, wrapping) that is associated with a pi session — or
   the next perspective when none is (D9 previously landed in the
   default perspective).
5. Close keeps the registry entry (mapping + captured specs);
   reopening restores the workspace.  Delete additionally deletes
   the session file — moved to the OS trash via the =trash= CLI when
   available, permanent unlink otherwise, mirroring pi's own TUI
   delete (=ctrl+d= in the session tree) — and drops the registry
   entry, so the session vanishes from both lists (the layer's list
   and pi's session manager both scan only =sessions/=).  Deleting a
   closed session (no active buffer) deletes its file and drops any
   registry entry; a perspective still registered for the file is
   torn down like an active session.  Deleting an active session is
   refused while its chat buffer is shared with another perspective
   (the file would move out from under a live process).

** D9a. Which file a delete removes; registry hygiene (2026)

The delete resolves the session file CHAT BUFFER FIRST, registry
second.  The chat buffer's settled =:session-file= is the ground
truth: a named session started inside the perspective (=a i S= → the
package's =pilish= command) moves the live file without a
registry update (the sync advice below now covers it, but the
registry can still be stale from before the first sync returns, and
process death before the get_state response leaves it stale for
good).  Resolving registry-first made =a i D= report "no session
file to delete" for remote sessions whose registry file was already
gone — or silently delete the WRONG session's file when it was not —
while the live file survived on disk.  The registry file is only the
fallback for perspectives whose chat buffer never settled (fresh
entries have no state file yet).  When the resolved file does not
exist on disk the delete still fails open with a message (a fresh
session pi never wrote): nothing to remove, nothing listable.

The trash step runs on the file's OWN host: =process-file= executes
its program on =default-directory='s host, so the trash lookup and
spawn bind =default-directory= to the file's directory.  A remote
file's =trash= is consulted only over an already-established
connection (I/O-free check — a delete must never open one); without
a remote trash, or for a local system without the CLI, the permanent
unlink remains.

Registry keys and =:session-file= values are stored and compared
property-stripped (=pilish//plain-string=): completion
pickers (helm) hand back strings carrying e.g. =helm-ff= properties,
and =equal=/=assoc= compare text properties — a property-laden entry
never matched again, so =registry-remove= kept deleted sessions
registered (pointing at deleted files), and lookups by name or file
missed.  =registry-load= strips on read, healing registries written
by older releases.

*** D10. New-session flow

=pilish/start-new-session=:
- Always prompts for the directory; the default follows =pilish/
  layout= logic (terminal cwd in terminals, recorded dir in pi buffers,
  buffer dir elsewhere).
- With existing sessions in the chosen directory, offers them through
  the unified picker (D2) — live ● first, then closed ○, with a
  section boundary, live sorted by directory then title, closed
  newest first: picking one opens/switches to it (with its layout),
  typing a fresh name (or picking the
  =✚ New session= candidate and entering one) starts a named session,
  an empty name starts an unnamed session.  Free-form input is
  authoritative: with =must-match= nil the helm action returns
  `helm-pattern` whenever the typed text is not exactly the selected
  candidate, and a dummy source offers the typed text as a candidate.
  Without it helm's substring/fuzzy matching hands back a merely
  similar existing session and RET opens it — the "type a new name,
  get the first item" bug.  Only an exact name match opens the existing
  session; the switch flow (=must-match= t) keeps plain candidate
  selection (no free input to prefer).  Rejected: disabling fuzzy
  matching for the picker (Spacemacs enables it globally, and plain
  substring matching already reopened a similar session), and reading
  the input back after helm exits (helm resets `helm-pattern`).
- Refuses an unnamed session when the directory already has a live unnamed
  session (package allows one unnamed chat buffer per dir); a name is then
  required for parallelism.  With no session files at all a fresh unnamed
  session starts directly.
- Fresh-session creation is one helper (=pilish//start-fresh-
  session=), shared with the bridge tool and the interactive command:
  create the perspective (placeholder label or the name, label-locked),
  =pilish--setup-session= (fresh, no resume), applies the layout,
  focuses input, registers the registry entry (session-file resolved
  lazily from chat state).
- =pilish/switch-session-in-dir= (SPC a i I) is the scoped
  switch: only the current directory's sessions (recorded dir in pi
  buffers, terminal cwd in terminals, visited file's dir elsewhere),
  same live-first ordering and section boundary (D2), current session
  excluded; switching re-applies the pi window layout.
- =pilish/new-worktree-session= names the worktree after the repo:
  the directory is =«root»/«repo-dir»-«suffix»= (a suffix already
  starting with the repo name is used as-is, avoiding a doubled
  prefix), so the owning repo stays visible and two repos sharing a
  suffix cannot collide.  The session is named after the combined
  directory.

*** D12. Pi-extension → Emacs bridge (tools that drive the hosting Emacs)

Goal: give sessions started by this Emacs frontend (pi --mode rpc
subprocesses) new LLM-callable tools that act on the hosting Emacs —
first one: open a new session at a tool-specified directory, creating
its perspective and switching to it.

Channel decision: the pi extension shells out to =emacsclient -e=
with a base64-encoded JSON request; Emacs evaluates the layer's
bridge entry (=pilish/open-session-at-directory-bridge=) and
returns a JSON string.  emacsclient -e is packet-based, synchronous,
request/response, and needs zero new infrastructure (an Emacs server
is the standard IPC).  Rejected alternatives:

- File mailbox + file-notify polling: works without a server, but
  adds latency, cleanup and a second channel to reason about.
- TCP/HTTP listener in Emacs (make-network-process): port/auth
  management, firewall prompts, an always-on service for a rare need.
- Extension-UI sub-protocol abuse (ctx.ui.*): one-way, no structured
  payloads, blocks the client UI protocols meant for dialogs.
- Upstream pi RPC change (generic extension→host messages): the
  correct long-term fix, but requires pi development; unnecessary for
  a local Emacs host that already owns the process.

Activation decision: the extension lives in the layer directory
(=pi-bridge-extension.ts=) and is wired via =pilish-extra-args=
=(-e <path>)= in =packages.el=, so exactly the sessions started by
this Emacs frontend get the tools — no global =~/.pi/agent/
extensions= pollution, no =INSIDE_EMACS= sniffing (Emacs does not set
that variable for subprocesses on this setup, verified).

Instance pinning: an around-advice on =pilish--start-process=
exports the Emacs server file to the pi process as =PI_EMACS_SERVER=;
the extension passes it to =emacsclient -s=, so the tool drives
exactly the Emacs instance that owns the session (correct with
daemons or several Emacs running).

Server guarantee: the channel needs a running server.  The layer
defcustom =pilish/enable-bridge= (default t) starts one at
layer load when none is running (skips batch and daemon — daemons
always serve).  Independent of =dotspacemacs-enable-server=.

Non-interactive contract: a server eval runs while the pi tool waits
on emacsclient, so bridge entry points must never prompt (no
completing-read, no y-or-n-p).  All failure paths return a JSON error
object instead of signalling.  The bridge entry binds the grammar
prompt state for the duration of the eval: essential grammars degrade
to ='warn= (deferred to an interactive open or M-x
pilish-install-grammars) and the optional-grammar question is
skipped — so a bridge call can never block on a minibuffer question.
Interactive session opens keep their normal prompting.  The extension
retries the emacsclient call once (3s backoff) to ride over slow first
setups or a transiently unresponsive server.

Tool: =emacs_new_session= {=directory=, =name=?}.  Mirrors the
=start-new-session= flow non-interactively: create+switch perspective
(«New session · path» or the name, label-locked when named), fresh
=pilish--setup-session= (no resume), registry entry, pi
window layout.  Refuses a second unnamed session for a directory that
already runs one (name opens a parallel named session).  Returns
={"ok": true, "persp": ..., "directory": ...}= or
={"ok": false, "error": ...}=; emacsclient prints the Lisp string,
so the extension double-parses (outer Lisp string literal, inner
JSON).

Trust note: any local process able to reach the Emacs server socket
can drive Emacs — the same trust boundary emacsclient already has.
Remote (Tramp) pi sessions are out of scope: the -e path is a local
file.

*** D11. Bindings

| Key       | Command                                | Note                              |
|-----------+----------------------------------------+-----------------------------------|
| SPC a i i | pilish/switch-session         | manager list (hub)                |
| SPC a i I | pilish/switch-session-in-dir  | switch current dir's sessions     |
| SPC a i n | pilish/start-new-session      | new with directory prompt         |
| SPC a i m | pilish/start-remote-session   | new on an ssh-config host (TRAMP) |
| SPC a i ? | pilish-menu                  | full transient menu               |
| SPC a i d | pilish/close-session          | close current session             |
| SPC a i N | pilish-new-session            | reset current (was on =n=)        |
| SPC m p i | pilish/switch-session         | mirror in chat/input mode leaders |
| SPC m p I | pilish/switch-session-in-dir  | mirror in chat/input mode leaders |
| SPC m p m | pilish/start-remote-session   | mirror in chat/input mode leaders |

=pilish-new-session= (package, reset current) moves from =n= to =N=.

Reset is an in-place package operation: the perspective is kept, the chat
buffer is cleared, and the pi process switches to a new JSONL session
file.  Other package commands switch the session file too: =resume=
(switch_session), =fork= / =fork-at-point= (fork), the direct
=open-session-file= (SPC a i s, switch_session), and =compact= (insurance;
pi rewrites the same file today).  The package never tells the layer
about any of these, so every such command carries =:after= advice
(=pilish//sync-registry-after-session-change=, installed by
=pilish//install-package-advices=) that issues its own
=get_state= and re-syncs the registry's =:session-file= (preserving
=:label-locked= / =:buffers=) plus the perspective label once the
process has settled on the new file.  RPC ordering guarantees the
=advice= get_state observes the switch (the session-changing RPC is
written first, pi processes RPCs in order); the fork path is advised at
=pilish--execute-fork= because the public =fork= command only
sends =get_fork_messages= and the =fork= RPC arrives later, after the
user picks a message.  Without this the stale registry would keep
listing the old file as opened, re-resume it on switch (undoing the
switch), and freeze the label on the old title.  Cancelled/failed/no-op
paths (completing-read cancelled, transition not ready, the layer's own
open flow) and no-registry-entry paths are no-ops.  Commands that do not
change the file need no sync: =reload= re-resumes the same cached file,
=set-session-name= is name-only (label advice), =quit= kills the process
only, and =pilish= / =open-named-session= stay registry-less by
design (the session list falls back to scanning perspective buffers).

** Architecture

- =pilish= layer (self-contained): registry + orchestration
  (capture/replay through persp's dispatch) + chat/input persp handlers +
  manager UI + close/new commands.  No dependency on my-persp.
- =my-persp= private layer (optional, generic, zero coupling): common-buffer
  injection + terminal save/load for the auto-resume domain.  Listed before
  =pilish= in =dotspacemacs-configuration-layers=.
- Registry file: cache directory (runtime state, not versioned dotfiles).

** Fail-open contract

- Registry read failure (missing/corrupt/unknown version): treat as empty;
  sessions still list and open from JSONL; one message logged.
- Per-spec restore failure: condition-case, skip, log to *Messages*;
  never aborts the open.
- Open ordering: perspective -> pi launch + resume (critical) -> layout ->
  buffer restore (best effort, last).  Pi never depends on restore.
- Registry writes are atomic (temp + rename).

** Out of scope (decided)

- Point saving (cursor positions): deferred to a future generic
  Emacs/persp extension; not a pi-layer concern.
- Window-configuration restore for closed sessions.
- Helm-specific session picker (two-source grouping): done — the
  unified picker (D2) renders live/closed as separate helm sources.
- Terminal process state restore (fresh shells in saved cwd only).
- Generic delete-all-buffers command: dropped.

** D13. Unified session listing (2026)

All session-listing commands (=switch-session=, =switch-session-in-dir=,
=start-new-session=, =close-session=, =delete-session=) share one model
(D2):

- Live sessions are always listed by their active pi chat buffers
  (=pilish//active-chat-buffers=), most recently used first.
  The old persp-mapping-based =opened= flag could mark a session live
  whose perspective had been killed (stale registry) or whose process
  had died, and could miss sessions started outside the registry
  flow; the buffer scan cannot lie.  A dead-process perspective's
  session now lists as closed; picking it still revives the
  perspective (the registry maps it).
- The builder =pilish//session-targets= (dir filter,
  include-closed, exclude-current) feeds every picker; dispatch is
  =pilish//open-or-switch-target= (live :buffer ->
  =pilish//switch-to-live-buffer=, closed :entry ->
  =pilish//open-or-switch=).
- Boundary: separate helm sources, header rows under completing-read
  (re-prompting when a header is selected).  Live always precedes
  closed; within a group the switch list sorts by
  =session-sort-opened= (default =dir-then-name= — directory, then
  title) / =session-sort-closed= (default =chrono= — newest first),
  close/delete keep most-recent-first.
- Fresh sessions without a JSONL file (pi writes it on the first
  response) are now listed as live candidates (label = perspective
  name), selectable like any other live session.

** D14. Remote (TRAMP) sessions via ssh-config hosts (2026)

=pilish/start-remote-session= (SPC a i m) gives the remote
flow a friendly entry point: pick a host from the ssh config, then
run the ordinary new-session flow (D10) on that host.

- The pi process itself runs on the remote host: the package's
  =pilish--start-process= already detects a TRAMP prefix in
  the session directory and starts pi over ssh
  (=make-process= with =:file-handler= plus a ready-marker protocol
  that queues RPC stdin until the remote process prints its marker),
  and checks dependencies against the remote PATH.  No layer code
  needed for the transport; the layer only supplies the host
  discovery.
- Hosts come from =pilish/ssh-config-file= (default
  =~/.ssh/config=): plain (non-wildcard) =Host= patterns in config
  order, =Include= directives followed recursively (depth-capped,
  globs expanded, relative paths per ssh_config(5) against =~/.ssh=
  for user configs), =Match= blocks skipped — a =Host= keyword
  terminates a =Match= block per ssh semantics, so such blocks parse
  as ordinary hosts.  =HostName= / =User= per host are collected for
  the alias filter and completion annotations (TRAMP resolves the
  connection itself via ssh).
- Alias filter: only hosts whose block declares a =HostName= field
  are offered — the host must be an alias for a real DNS name.
  Entries that are already direct hostnames, or that only set
  options like =User= / =IdentityFile=, are filtered out.  Option
  lines attach to every plain pattern of a =Host= line, so
  =Host alpha beta= + =HostName x= lists both.
- Single alias: used without prompting (a config with one alias
  makes the picker ceremony); several aliases: =completing-read=
  with annotations; none: user-error pointing at =SPC a i n= with a
  =/ssh:HOST:path= directory.
- Connection hardening: the first TRAMP connection (which resolves
  the remote home for the directory-prompt default) happens in an
  explicit pre-flight step with a =Connecting to HOST ...= message
  and a clear error naming the host, instead of inside
  =read-file-name='s default expansion where a hang is opaque.  An
  ssh =ConnectTimeout= (=pilish/remote-connect-timeout=,
  default 20s) is injected via the =login-args= connection property
  — which REPLACES the method's args, so the full ssh arg list is
  rebuilt with =%h/=/%u/=/%p/=/%c= intact — because TRAMP's own
  =tramp-connection-timeout= is not reliably enforced while waiting
  on ssh (verified empirically).  The directory prompt then defaults
  to the canonical home (no =~=), so the prompt itself triggers no
  hidden connection.
- The directory prompt defaults to =/ssh:HOST:~= (remote home); the
  route-preserving path helpers keep the TRAMP prefix byte-for-byte
  intact through the whole flow.
- Closed-session scan on the remote host: the picker's scan
  (=pilish//session-entries=) takes an optional ROOT, and
  the remote flow scans =<prefix>~/.pi/agent/sessions/= — the remote
  pi's default agent dir; the local =PI_AGENT_DIR= override is not
  forwarded by TRAMP, so it is deliberately not applied remotely.
  Remote scans are best-effort: connection failures yield an empty
  closed list instead of blocking the picker.
- Remote path canonicalization: session headers record the
  process-local cwd, so remote entries' =:cwd= is anchored to the
  file's TRAMP prefix (=pilish//entry-cwd=), and
  =pilish//normalized-dir= canonicalizes remote dirs through
  TRAMP (=expand-file-name= expands the =~= home component).  One
  remote directory therefore compares equal regardless of =~=
  spelling, which keeps session identity (buffer names, the
  unnamed-session refusal, the live/closed lists) consistent; the
  chosen dir is canonicalized before entering the new-session flow.
- The pi spawn is independent of the remote PATH — both for finding
  pi and for resolving its shebang: the TRAMP spawn shell is a
  non-interactive login shell (rc files skipped on purpose, above),
  so a user-installed node (e.g. pi's managed
  =~/.local/share/pi-node/<ver>/bin=, put on PATH only by an
  interactive rc file) is invisible to it and pi's
  =#!/usr/bin/env node= shebang dies with exit 127 ("env: node: No
  such file or directory") right after the ready marker.  The
  mapping's NODE-PATH is therefore not just recorded but USED:
  =pilish//remote-spawn-executable= wraps the spawn in
  =sh -c 'PATH=<node-dir>:$PATH; export PATH; exec "$0" "$@"'= —
  the same treatment =pilish//remote-verify-pi= gives its
  verification run — and composes with the package's own remote
  wrapper (ready marker + =exec "$0" "$@"=, whose =$0= becomes our
  =sh=).  Applied to every remote spawn via the
  =pilish//remote-spawn-start-process= advice on
  =pilish--start-process=, so opens from the session list
  (SPC a i i / SPC a i S), =SPC a i s= and revivals get it without
  binding anything themselves; hosts without a mapping spawn as
  before (fail-open).  The same advice drops local-only =-e=
  extension pairs (=pilish//remote-extra-args=): the remote
  pi aborts with "Extension path does not exist" otherwise.  Note
  =pilish-extra-args= needs its =defvar= declaration at the
  top of funcs.el (lexical-binding pitfall, file header): the first
  version of the start-remote-session filter was byte-compiled into
  an ineffective lexical binding and never filtered anything.
- Key choice: =m= (machine) for the remote-session flow; the
  transient menu moves from =m= to =?= (=SPC a i ?=) to free it,
  keeping the menu on =p= in the chat/input mode leaders.  Mirrored
  as =SPC m p m= in the chat/input mode leaders.

** D15. Session-list scope and non-blocking remote listing (2026)

The non-blocking remote-listing contract below is the durable part of
these decisions and is carried forward by D16; the switch-session
scope it describes (current session's host only) was widened into
the per-host hub of D16, which supersedes it for =SPC a i i=.

- Scope (as of D16, =SPC a i i= lists every host in
  =pilish//known-remote-prefixes=): a local context with no
  known remote hosts lists LOCAL sessions only — remote sessions
  never appear in the list, and no remote file is ever touched, so a
  dead remote host cannot hang the listing.  Used inside a remote
  (TRAMP) session, the list adds that host's sessions: its live chat
  buffers plus its closed session files, scanned on the remote host.
- The scope is the current perspective's pi chat buffer's remote
  prefix (=pilish//current-session-remote-prefix=): no
  session → local scope.  =pilish//session-targets= takes a
  REMOTE-SCOPE: =local= (local sessions only), a TRAMP prefix string
  (local sessions plus that host's live buffers and closed files), a
  list of TRAMP prefixes (D16: the switch hub — local sessions plus
  exactly those hosts), or =t= (local sessions plus every active
  remote host's — the close/delete scope, which must reach a dead
  remote session).
  Every picker is built by this one function; the commands differ
  only in the scope and in whether closed sessions are included
  (both include them) and whether the current session is excluded
  (switch excludes it, close/delete offer it as the default).
  Rejected: leaving the close/delete pickers unscoped with a
  half-remote list (live buffers of all hosts, closed files of none)
  — the same session appeared in one picker but not the other, and a
  closed remote session could never be deleted at all.
- Session metadata is read through
  =pilish//session-scan-info=, which resolves the package's
  scanner at runtime with =fboundp=: the scanner name moved between
  package releases (=pilish-jsonl-read-session-info= →
  =pilish-jsonl-read-session-info=; older versions ship
  =pilish--session-metadata=).  Calling a missing name
  directly made EVERY metadata read fail (the fail-open condition-case
  swallowed the void-function error per file), which silently emptied
  the closed-session lists — the scanner must be resolved, never
  assumed.
- Connection gating: remote work in the listing path happens only
  over an already-established TRAMP connection
  (=pilish//tramp-connection-alive-p= — an I/O-free check:
  dissect the file name, look up the connection's ssh process via
  =tramp-get-connection-process=, =process-live-p=).  A disconnected
  host gets a background ssh probe
  (=pilish//remote-probe-async=, BatchMode + ConnectTimeout,
  throttled per host) and contributes nothing to the list — the local
  part shows immediately; the host's closed sessions reappear in a
  later listing once the probe succeeds.  This is the listing-side
  answer to the same TRAMP untimeoutable-wait failure D14 probes
  around: TRAMP's own timeouts never fire while its wait loop holds
  the input, so remote I/O must simply never start from a listing.
- Fail-open metadata: =pilish//session-metadata-cached= and
  =pilish//session-file-cwd= never touch a remote file whose
  connection is not established — a stale cache entry is returned
  without mtime validation when present, otherwise the entry is
  dropped; =pilish//sync-labels= skips disconnected remote
  entries entirely (the stale-title fallback would rename the label
  to title-only, undone by the next connected listing).  The session
  cache eviction in =pilish//session-entries= is scoped to
  the scanned root, so local scans never wipe remote hosts' cached
  metadata.
- Opening a remote session whose connection is not established probes
  the host with the bounded ssh deadline first
  (=pilish//ensure-remote-reachable= in
  =pilish//open-or-switch=): reachable/auth hosts fall
  through (TRAMP prompts interactively), unreachable hosts fail with
  a clear error instead of hanging.  The open also binds the host's
  verified executable mapping
  (=pilish//remote-executable-for= from
  =pilish/remote-executables=), matching
  =pilish/start-remote-session='s spawn, so sessions picked
  from the scoped list spawn the remote pi correctly.
- Switch-in-dir follows the directory: a remote DIR's listing scans
  that host's session root over the established connection
  (=pilish//remote-scan-root=), nothing remote when the host
  is unreachable.
- Drive-by: =pilish//remote-locate-executables= now deletes
  stale mapping entries with =assoc-delete-all= — the previous
  =assq-delete-all= never matched string keys, so the saved custom
  accumulated a duplicate per-host entry per re-verification.

** D16. Switch-session hub: per-host remote sections (2026)

=pilish/switch-session= (SPC a i i) grows from "local, plus
the current remote session's host" to a hub over every host the
layer knows runs pi, and remote sessions are displayed grouped by
host instead of mixed into the live/closed lists.

- Scope: the hub lists local sessions plus the sessions of every
  host in =pilish//known-remote-prefixes= — hosts with
  verified executables in =pilish/remote-executables= (the
  persisted machines =start-remote-session= has located pi on),
  hosts of active pi chat buffers, and the current session's host.
  The enumeration is purely local (a custom read plus buffer state),
  so a dead host cannot cost anything up front.  With no such hosts
  the scope is exactly D15's local-only behavior.  Rejected: reading
  the ssh config for candidate hosts (noise — most ssh hosts never
  run pi, and each would fire a background probe) and scanning the
  session cache for remote keys (volatile per Emacs run, so hosts
  would disappear after a restart until reconnected).
- Remote-scope lists: =pilish//session-targets= now admits a
  list of TRAMP prefixes (exactly those hosts) besides the D15
  string / =t= forms, via =pilish//remote-scope-prefixes=;
  close/delete still pass =t= and are unchanged.  Listing a scoped
  host keeps D15's contract — live chat buffers from local state,
  closed files scanned only over an already-established connection,
  otherwise a background probe and no contribution — so a
  disconnected host is best-effort and never blocks Emacs.
- Rendering: the switch list becomes ordered sections: local live
  sessions under "Live sessions", one section per remote host
  (named after the host, hosts sorted by name) between the two local
  groups, then local closed sessions under "Closed sessions".  Each
  host section lists its host's live candidates (●) before its
  closed ones (○), each keeping its group's sort order
  (=session-sort-opened= / =session-sort-closed=).  Sections with no
  candidates are omitted, so the classic two-group layout renders
  unchanged when nothing remote is in scope.
- Picker generalization: =pilish//pick-session-sections=
  renders an ordered list of (NAME . ALIST) sections — one helm
  source or completing-read header row per section, boundaries
  between groups, empty sections skipped; the old live/closed
  picker is now the two-section wrapper around it, so
  new-session/close/delete keep their exact previous layout.
  Section headers were previously two hardcoded boundary constants;
  the generic =session-header= row is derived from the section name,
  which is what lets a host name become a section.
- Rejected: splitting a remote host's section into its own nested
  live/closed sub-groups.  The status glyphs (●/○) already carry
  that distinction, and helm/vertico render one flat row set per
  section; nested headers would add a third layer of boundaries to
  a list that is already host-grouped.

** Implementation notes

- Session-list scan caches per-file metadata keyed by mtime; only changed
  files are re-parsed (hundreds of sessions stay fast).
- New sessions may not have a session file until pi writes one; the registry
  entry stores dir and resolves session-file lazily from chat buffer state.
- Missing-file behavior on registry replay: tune at implementation
  (skip vs. persp's default empty-buffer fallback).
- Label placeholder ("New session") updates to the first-message snippet via
  the lazy scan sync after the first prompt.

** D17. Chat/input windows stay put via window-purpose (2026)

=find-file= (=SPC f f=), =C-x b=, and friends in a pi chat/input window
used to replace that window's session buffer with the newly opened
buffer.  The windows now stay on their session buffers and the new buffer
lands in the general (edit) window.

- The routing is window-purpose's own: the layout marks the chat and
  input windows =:purpose-dedicated t=.  window-purpose's
  =purpose-display--frame-usable-windows= (=display-buffer=) and
  =purpose-display-maybe-same-window= (the advised
  =switch-to-buffer=/=pop-to-buffer=) both refuse a purpose-dedicated
  window whose purpose differs from the buffer's, so every routed
  command goes to the general window.  There is no Emacs window
  dedication.
- One path bypasses purpose entirely: a caller that hands a buffer
  straight to =set-window-buffer= on a window it picked itself.
  Spacemacs' helm action =spacemacs//helm-open-buffers-in-windows= does
  exactly that — it maps buffers onto windows by =winum= number, calling
  =set-window-buffer= on each — which is what put the opened file into
  the input window.  This is generic window-purpose behavior, not pi
  behavior, so the guard that covers it now lives in the =purpose-fix=
  layer (=purpose-fix//keep-dedicated-window=).  It keys on
  window-purpose's own =purpose-dedicated= window parameter — the same
  rule the package's display functions apply — and exempts the callers
  that own window assignment: the package's
  =purpose-set-window-properties=/=purpose-set-window-purpose= and
  =window-state-put=, which persp-mode uses to restore a perspective's
  window state when a session is switched to (=SPC a i i=).  Those
  assign buffers in place, so a window still carries its pre-restore
  purpose while the state's buffer is being set and judging it by that
  purpose would scramble the restored layout.
  It diverts a foreign buffer to a fitting window and, when the buffer
  was headed for the *selected* window, moves the focus with it
  (=set-window-buffer= cannot select a window, so a caller that bypasses
  purpose would otherwise leave the user in an unchanged window while
  the buffer opens elsewhere).  See the layer's README for the full
  rationale and the rejected alternatives.
- Rejected: Emacs window dedication (=set-window-dedicated-p ... t= or
  ='side=).  Strong dedication turns that same direct
  =set-window-buffer= into "Window is dedicated" and then needs more
  machinery (advices on the package's display functions plus a
  =switch-to-buffer-in-dedicated-window= override) to keep the package's
  own display working; soft =side= still lets
  =switch-to-buffer=/=set-window-buffer= replace the window.
- Rejected: a =display-buffer-alist= entry avoiding the pi buffers by
  name.  It would not affect =switch-to-buffer=/=set-window-buffer=
  (which do not consult the alist) and would duplicate window-purpose's
  purpose routing.

** D18. The Default pseudo-perspective is not a perspective (2026)

persp-mode 4.0 (MELPA 20260830.105) represents the default perspective —
Spacemacs names it =Default=, =persp-nil-name= — as a =persp-nil-persp=
structure.  Through 2025 it *was* nil, which is what the layer's
perspective queries were written against: =persp-get-by-name= answered
nil for that name, =perspective-p= rejected it, and only the
nil-tolerant =persp-p= accepted it.  Now the lookup returns the
structure and =perspective-p= accepts it, while =persp-contain-buffer-p=
still answers t for it whatever the buffer — so "which perspectives are
there?" questions started counting =Default= as one, and "does another
perspective share this buffer?" started answering yes.

That made =pilish//exclusive-buffers= — the buffers only this
perspective has — nil for every perspective, because =Default= claimed
them all.  Two commands read that list for their safety:

- =SPC a i D= (=pilish/delete-session=) refuses a session whose chat
  buffer is shared with another perspective (the session file would move
  out from under a live process); with an empty list every session
  looked shared, so every delete was refused.
- =SPC a i d= (=pilish/close-session=) stops the pi process and kills
  the session's buffers before killing the perspective.  With nothing
  "exclusive" it skipped both and killed the perspective, orphaning a
  live pi process together with its chat/input buffers.

Rule: the default pseudo-perspective is not a perspective.  Where the
question is "is this a perspective that can own a pi session, or
another perspective that might share a buffer", ask
=pilish//real-persp-p= instead of =perspective-p=:
=pilish//exclusive-buffers= (the other-perspective check),
=pilish//persp-containing-buffer=, =pilish//ordered-persp-names= (which
supplies "the next perspective" after a close), =pilish//persp-for-close=
and the session list's =exclude-current= gate.  The predicate compares
=safe-persp-name= against =persp-nil-name=, which holds for both
representations (in the old one the lookup answers nil, failing the
=persp= test first) and for a renamed default perspective.  Sites that
gate on =pilish//chat-buffer-in-persp= need no change: the
pseudo-perspective hosts no pi session.

Rejected: pinning persp-mode to the old version.  The structure is
upstream's design (=persp-nil-persp=, the =persp-persp-*= accessors),
and the layer's assumption was version-specific rather than a promise
the package ever made.

The rest of 4.0's renames (=get-current-persp= → =persp-get-current=,
=safe-persp-name= → =persp-name=, ...) keep obsolete aliases that the
layer still calls; that part is cosmetic and can migrate separately.
