* pilish layer

This layer installs and configures the
[[https://github.com/dnouri/pilish][pilish]] Emacs frontend
for the [[https://pi.dev][pi coding agent]]. It provides a two-window
interface for AI-assisted coding: a chat buffer with rendered markdown and a
separate prompt composition buffer, backed by a =pi --mode rpc= subprocess.

By default the package is installed with quelpa from this config's fork
([[https://github.com/tigersoldier/pi-coding-agent][tigersoldier/pi-coding-agent]],
branch =downstream=), which carries fixes not yet released upstream.  On a
development device, create the gitignored =pilish/local/config.el= with

#+begin_src emacs-lisp
(setq pilish/use-local-checkout t)
#+end_src

and symlink the checkout to =pilish/local/pilish=; the layer then loads that
checkout (=:location local=) instead of installing the package.  The flag is
a layer defcustom, but it lives in the local file because =packages.el=
reads it before the layer's =config.el= is loaded.

** Prerequisites

- Emacs 29.1 or later with tree-sitter support
- pi coding agent =@earendil-works/pi-coding-agent= 0.81.0 or later,
  installed and in PATH, e.g.:

#+begin_src sh
npm install -g @earendil-works/pi-coding-agent
#+end_src

The layer adds =~/.local/bin=, =~/bin= and =/usr/local/bin= to
=exec-path= if they contain the =pi= binary, so GUI-launched Emacs
finds it even without the interactive shell's PATH.

Tree-sitter grammars for markdown are installed automatically on first
session start (or manually via =pilish-install-grammars=).

** What it does

- Declares the =pilish= package (its dependencies =transient=,
  =md-ts-mode= and =markdown-table-wrap= are pulled in by package.el);
  the package itself comes from the fork's =downstream= branch via
  quelpa unless =pilish/use-local-checkout= selects a local checkout.
- Keeps the package's own behavior: sessions are per-project (one
  process per directory, optionally named for parallel sessions),
  Evil keybindings load automatically when Evil is present, and the
  built-in =C-c= bindings in chat/input buffers are unchanged.
- Adds Spacemacs leader keybindings (see below).
- Sets =pilish-project-trust-policy= to =approve=, so
  project-local =.pi= prompts, skills, settings, themes, and
  extensions are available in RPC mode (which has no interactive
  trust prompt).
- Requires the =spacemacs-layouts= layer (persp-mode): each opened pi
  session is a perspective (a workspace with its own buffer set).
- Adds session management: a global session list, new-session with
  directory prompt, and close-session (see below).

** Session management

Every opened pi session is a persp-mode perspective — "like a project":
the buffers you open while in the session (files, terminals, pi
chat/input) belong to that perspective, and =SPC b b= only shows the
current perspective's buffers plus common buffers (=*scratch*=,
=*Messages*=; see the optional =my-persp= layer below).  =SPC b B=
shows all buffers.

All session pickers share one list model: **live sessions** are the
active pi chat buffers (sessions whose pi process is alive), listed
most recently used first; **closed sessions** are the session files on
disk not loaded by a live session.  Whenever both are listed, live
sessions come first, separated from the closed ones by a section
boundary — separate =Live sessions= / =Closed sessions= sources under
helm, header rows otherwise.  Each candidate is annotated with a
status glyph (● live / ○ closed), message count, and age; titles
collapse newlines to single spaces so every session is exactly one
row.

- =SPC a i i= (=pilish/switch-session=) — list all pi
  sessions (the current one is excluded) grouped into sections: the
  local machine's live sessions (●) under =Live sessions=, one
  section per remote host with sessions — named after the host, the
  hosts sorted by name — between the two local groups, then the local
  closed sessions (○) under =Closed sessions=.  Within each section
  live sessions sort by directory, then by title; closed sessions by
  recency, newest first (descending) (a remote host section lists its
  host's live sessions first, then its closed ones).  Selecting a
  live session switches to its perspective; selecting a closed session
  opens it: a new perspective is created, the pi process is started,
  the session file is resumed, and the previously remembered workspace
  buffers are restored (a dead perspective still registered for the
  session is revived instead).  Reopening always gets its own
  chat/input buffers and process — even when the directory already
  runs another session, the reopened one is opened side-by-side under
  its recorded name (or a generated name for an unnamed session) rather
  than reusing the live session's buffers.  Sort orders are configurable:
  =pilish/session-sort-opened= (default =dir-then-name=
  — directory, then title) and =pilish/session-sort-closed=
  (default =chrono= — newest first).  Scope: local sessions are always
  listed; a remote host joins the listing whenever the layer knows it
  runs pi sessions — hosts with verified executables in
  =pilish/remote-executables=, hosts of active pi chat
  buffers, and the current session's host.  Listing a remote host is
  best effort and never blocks: its live chat buffers come from local
  state and its closed files are scanned only over an
  already-established TRAMP connection; a disconnected host is probed
  in the background and contributes no section to this listing — its
  sessions reappear in a later listing once it answers.
- =SPC a i I= (=pilish/switch-session-in-dir=) — switch
  between the current directory's pi sessions, applying the pi window
  layout afterwards.  The directory is the session's own directory
  inside pi chat/input buffers, the terminal's working directory in
  terminal buffers, and the visited file's directory (else
  =default-directory=) elsewhere.  Same list as =SPC a i i= but scoped:
  live (●) first, then closed (○), with the same section boundary,
  live sorted by directory then title, closed newest first; the
  current session is excluded.
- =SPC a i n= (=pilish/start-new-session=) — start a brand
  new session: always prompts for the directory (the default follows
  the layout's directory logic — terminal cwd, session dir inside pi
  buffers, buffer dir elsewhere).  When the directory has existing
  sessions, they are offered for selection (live ● first, then
  closed ○, with a section boundary between the groups, live sorted
  by directory then title, closed newest first) via the unified
  session picker, so it works with helm,
  ivy, vertico or the plain minibuffer: picking an existing session
  opens or switches to it (with its layout), typing a new session name
  (or picking the =✚ New session= candidate and entering one) starts a
  fresh named session, and an empty name starts an unnamed session —
  refused when the directory already runs a live unnamed session (then
  a name is required for the parallel session).  A typed name wins
  over a merely similar candidate (a fuzzy/substring match must not
  silently open the wrong session); only an exact name match opens the
  existing session.  With no existing
  sessions a fresh unnamed session starts directly.
- =SPC a i m= (=pilish/start-remote-session=) — start a new
  session on a remote host, the same flow as =SPC a i n= but with the
  directory on a host from the ssh config (=pilish/ssh-config-file=,
  default =~/.ssh/config=; =Include= directives are followed,
  wildcard patterns and =Match= blocks skipped).  Only host
  *aliases* are offered — `Host' entries whose block declares a
  =HostName= field pointing at the real DNS name; entries that are
  already direct hostnames (or only set =User=/=IdentityFile=) are
  filtered out.  With exactly one alias it is used without
  prompting; with several the aliases are offered for selection
  (annotated with their =HostName= and =User=).  Then the normal
  new-session flow runs on that host:
  the directory prompt defaults to the host's home (=/ssh:HOST:~=),
  existing sessions of that directory are offered — the closed list
  is scanned on the remote host — and a fresh session starts
  otherwise.  The pi process itself runs on the remote host through
  TRAMP (the package starts it over ssh), so the host needs the pi
  CLI installed and reachable via =ssh HOST=.
- =SPC a i d= (=pilish/close-session=) — close a pi session:
  the current perspective's session when it has one, otherwise the
  live sessions are listed (active pi chat buffers; the perspective
  is resolved from the chosen buffer).  Stops the pi process, kills
  the perspective's buffers (standard unsaved-change prompts; common
  buffers and buffers shared with other perspectives are spared),
  and removes the perspective.  Afterwards Emacs lands in the next
  perspective that has a pi session (or the next perspective when
  none does).  The workspace is remembered, so reopening the session
  from the list restores its buffers.
- =SPC a i D= (=pilish/delete-session=) — delete a session
  and remove it from the session list.  Always prompts — the current
  session is the default — offering both live sessions (active pi
  chat buffers) and closed sessions, live first with a section
  boundary (separate sources under helm).  The list is built by the
  same logic as =SPC a i i=, scoped wider: every host's sessions are
  offered (a dead remote session can be reached and deleted), with
  remote closed files scanned only over established connections.  An
  active session is
  closed like =SPC a i d=, then its file is deleted — moved to the OS
  trash via the =trash= command when available, otherwise deleted
  permanently, the same behavior as pi's own TUI delete (=ctrl+d= in
  the session tree) — and its registry entry dropped; a closed session is
  deleted the same way (a dead perspective still registered for it
  is torn down too).  Either way the session no longer appears in
  the session list — neither this layer's nor pi's own.  Deleting an
  active session is refused while its chat buffer is shared with
  another perspective (the file would move out from under a live
  process).
- =SPC a i w= (=pilish/new-worktree-session=) — create a
  fresh git worktree and start a pi session in it.  Picks a git
  repository via helm (known repos from the context directory,
  =projectile-known-projects=, and one level under each
  =pilish/repo-roots= entry are offered; any path can be
  typed — re-prompting until it is inside a repository), then
  prompts for a suffix naming the worktree directory under
  =pilish/workspace-root= (default =~/work=).  The worktree directory
  combines the repository's directory name with the suffix, so the
  owning repo stays visible: repo =foo= with suffix =fix= creates
  =«root»/foo-fix= (a suffix already starting with the repo name is
  used as-is, avoiding a doubled prefix).  The repo's
  mainline branch (=origin/main=, else =origin/master=, else the
  local =main=/=master=) is fetched best-effort (timeout-capped,
  failures ignored) and checked out in the worktree — detached at
  the remote-tracking tip when the branch comes from origin,
  attached when it is a free local branch.  The new pi session (own
  perspective, pi window layout) is named after that combined
  directory name.
- =SPC a i W= (=pilish/new-workspace-session=) — create a
  workspace with git worktrees and start a pi session in it.  Picks
  one or more git repositories via helm multi-select
  (=pilish/repo-mark-key=, default =C-;=, marks several;
  =RET= confirms; same candidates as above, any path can be typed),
  then prompts for the workspace name.  Creates
  =«root»/«name»/repos= with one worktree per repository (mainline
  branch as above, fetched best-effort), named after the
  repository's directory (uniquified with =-2=/-3=/… on
  collisions).  The new pi session (own perspective, pi window
  layout) is named after the workspace.
- =SPC a i N= — reset the current session (=pilish-new-session=,
  moved from =n=).  The perspective is kept, the chat buffer is cleared,
  and the pi process switches to a new JSONL session file; the registry
  mapping and the perspective label (back to the =New session= placeholder
  until the first message) are re-synced automatically afterwards.

  The same automatic re-sync covers every other package command that
  switches the session file in place: resume (menu =r=, =C-c C-r=,
  =/resume=), fork (=f=, =/fork=), the direct =SPC a i s= session-file
  open, and =compact= (file unchanged today; kept honest if pi ever
  changes that).  The perspective label follows the newly loaded session
  (=/name=, else first-message snippet), so resuming an older session
  renames the perspective accordingly (unless you locked it with
  =SPC l r=).

Perspectives are named =«title» · «abbrev-path»= (e.g. =Refactor auth ·
~/.emacs.d=); the title follows the session =/name=, else the first
message, else =New session= until the first prompt.  Renaming the
session (package command or =/name=) updates the perspective label;
renaming the perspective yourself (=SPC l r=) locks the label.

** Session restore after restart

Pi processes die with Emacs; what comes back after a restart depends
on =dotspacemacs-auto-resume-layouts=:

- =nil= (default): all sessions are closed after a restart.  Use
  =SPC a i i= to reopen them — the registry restores each session's
  workspace buffers.
- =t=: persp-mode restores every perspective with its buffers at
  startup — files (persp defaults), terminals (if the =my-persp= layer
  is enabled), and the pi session itself (chat/input buffers are
  re-opened and the session file resumed).  Caveat: N sessions mean N
  pi processes spawning at startup.

Session metadata (perspective ↔ session file mapping, captured buffer
specs) is stored in the registry file under
=spacemacs-cache-directory= =/pilish/registry.el= (runtime
state, not dotfiles).  The registry fails open: if it is missing or
corrupt, sessions still list and open from the JSONL files — only the
workspace-buffer memory is lost.

** Optional: the =my-persp= layer

A small private layer (=private/my-persp=, listed before
=pilish=) that enhances persp-mode generically, with zero
coupling to this layer:

- Common buffers (=*scratch*=, =*Messages*=; configurable via
  =my-persp-common-buffer-regexps=) are injected into every
  perspective, so they stay reachable from =SPC b b= in any layout.
- Terminal buffers (vterm, term, eshell, shell) are saved to persp
  state with their real working directory (vterm via
  =/proc/<pid>/cwd=) and relaunched there on restore.

Without =my-persp= the pi layer still works end to end; only terminals
are not restored across restarts, and common buffers are not visible
inside session perspectives.

** Usage

- =SPC a i i= — list all sessions (local live, one section per remote
  host, then local closed): open the chosen one or switch to it
- =SPC a i I= — switch between the current directory's sessions (with layout)
- =SPC a i p= — start or focus the pi session for the current project
- =SPC a i n= — start a new session (asks for the directory)
- =SPC a i m= — start a new session on a remote ssh-config alias (TRAMP)
- =SPC a i d= — close a session (and its workspace)
- =SPC a i D= — delete a session (moved to trash; prompts, default: current)
- =SPC a i l= — apply the saved window layout (start/focus a session)
- =SPC a i t= — hide/show the pi windows
- =SPC a i ?= — full transient menu (model, thinking level, sessions, …)
- =SPC a i S= — start a named (parallel) session
- =SPC a i N= — reset / new session in the current directory

** Driving Emacs from pi sessions (bridge)

Sessions started by this Emacs frontend load a small pi extension
(=pi-bridge-extension.ts= in this layer) that registers tools the
agent can call to act on the hosting Emacs:

- =emacs_new_session= — open a brand-new pi session in another
directory.  Emacs creates a new perspective (workspace), starts the
session there, applies the pi window layout, and switches to it —
the same flow as =SPC a i n=, driven by the agent.  Parameters:

  - =directory= (required) — absolute or ~-style path; must exist.
  - =name= (optional) — session name; required to open a parallel
    session when the directory already runs an unnamed session.

The extension talks to Emacs over =emacsclient -e= (request/response
JSON over the Emacs server socket).  The layer ensures a server is
running when the bridge is enabled, and exports the socket path to
pi processes as =PI_EMACS_SERVER= so the tool always drives the Emacs
instance that owns the session (safe with daemons / multiple Emacs).

Configuration:

- =pilish/enable-bridge= (default =t=) — master switch:
  adds the extension to every pi command and starts the Emacs server
  if none is running (independent of =dotspacemacs-enable-server=;
  daemons always serve).  Set to =nil= to disable.
- The extension is added via =pilish-extra-args= =(-e ...)=;
  only sessions started after loading the layer get the tools.

Notes:

- The bridge entry points never prompt (they run while the pi tool
  waits on emacsclient); failures are returned as JSON errors the
  agent reports.
- Any local process with access to the Emacs server socket can drive
  Emacs — the standard emacsclient trust boundary.
- Remote (Tramp) pi sessions are not covered by the -e extension
  flag.

** Window layout

The layer ships a purpose window layout (=pilish.window-layout=,
loadable with =SPC a i l=):

#+begin_example
+-------------------------+-------------------------+
| pilish-chat    |                         |
| (70% height)            | any                     |
+-------------------------+ buffer                 |
| pilish-input   |                         |
| (30% height)            |                         |
+-------------------------+-------------------------+
#+end_example

The left column (chat + input) takes =pilish/layout-width-ratio=
of the frame width (default =0.5=); the right =edit= pane takes the rest.
=pilish/layout= builds the layout from that variable at apply
time, so changing it takes effect on the next =SPC a i l=.

- The chat and input buffers have dedicated purposes (=pi-chat= /
  =pi-input=) mapped from the package's modes in =config.el=, so they
  are always routed to the left panes.
- The right pane uses the =edit= purpose and is not dedicated, so it
  can hold any buffer — and since file-visiting buffers classify as
  =edit=, the fill loop fills it with an existing buffer instead of
  creating a dummy.  =pilish/layout= restores the buffer you
  were in before the command to that pane; when the command is run
  from a pi buffer, it shows the most recently used non-pi buffer
  instead (and drops window-purpose's dummy placeholders).
- The layer directory is registered in =purpose-layout-dirs=, so the
  static default layout (=pilish.window-layout=, kept in sync
  with the variable's default) is also available via
  =M-x purpose-load-window-layout=.
- =pilish/layout= refreshes the purpose tables first and
  re-asserts the session buffers in their panes, so it works even
  after layer reloads (=SPC f e R=) that leave purpose-mode's compiled
  tables stale.
- =pilish/layout= never starts a new pi process when a
  session already exists: it reuses the current directory's session,
  falling back to the most recently used live session.  Only when no
  session exists at all does it start one, choosing the directory as
  follows:
  - inside pi chat/input buffers, the session's recorded directory is
    reused (this also revives a session whose process died);
  - inside a terminal buffer (vterm, ansi-term/term incl. multi-term,
    eshell, shell-mode), the terminal's current working directory is
    used — term-mode via `term-command-hook', shell-mode via dirtrack
    and eshell natively keep `default-directory' in sync with the
    shell's cwd; vterm only updates it from OSC 7 (which plain zsh
    never emits), so its real cwd is read from the process's
    `/proc/<pid>/cwd' symlink instead.  When the real cwd cannot be
    determined (unreadable `/proc', dead terminal process), the user
    is prompted for the directory with `default-directory' as the
    default instead of silently using a possibly-stale value;
  - anywhere else, the user is prompted for the directory, defaulting
    to the current buffer's directory (the visited file's directory,
    or `default-directory').  Cancelling the prompt aborts the command.

Inside a pi buffer:

- =C-<return>= — send prompt (Ctrl+Enter, like other coding agents; =RET=
  in insert state stays a literal newline for multi-line prompts)
- =C-c C-c= — send prompt (queues as follow-up if busy)
- =C-c C-s= — queue steering (interrupts after current tool)
- =C-c C-p= — open the transient menu
- =C-c C-r= — resume a session
- =C-c C-k= — abort current operation
- =TAB= / =@= — path completion / file references in the input buffer

** Configuration

Package options are set in the =init= function in =packages.el=:

- =pilish-evil-integration= — load Evil keybindings (default =t=)
- =pilish-project-trust-policy= — =approve= (default) /
  =default= / =no-approve=
- =pilish-input-window-height= — height of the input window
  (set it in =config.el= or via =M-x customize-group pilish=)

Layer option (defined in =config.el=):

- =pilish/layout-width-ratio= — fraction of the frame width
  taken by the pi left column (chat + input), default =0.5=.  Set it
  in =dotspacemacs/user-config=, e.g.
  #+begin_src emacs-lisp
  (setq pilish/layout-width-ratio 0.4)
  #+end_src
  or via =M-x customize-group pilish=, then re-apply with
  =SPC a i l=.
- =pilish/remote-connect-timeout= — seconds allowed for the
  initial TRAMP connection of =SPC a i m= (default =20=; an ssh
  =ConnectTimeout= is passed, so an unreachable host fails with a
  clear error instead of hanging on =Opening connection ...=).  Set
  to =nil= to keep TRAMP's own defaults.
