* pi-coding-agent: session management design

Design decisions for extending the =pi-coding-agent= layer with Emacs <-> pi
session management.  Recorded during a grilling session on 2026-08-09.  This
document captures the agreed design; the layer README describes implemented
behavior.

** Context

The layer currently wraps the MELPA =pi-coding-agent= frontend (RPC-backed
chat/input buffers) and adds a purpose window layout, launch-directory
resolution, and leader keybindings.  The package itself already provides
per-project sessions, named parallel sessions, a transient menu (new/resume/
fork/name/model), and per-directory session resumption.

The goal: a session management solution where each opened pi session behaves
like a project — a workspace with its own buffer set, restorable across
closes and restarts.

** Decisions

*** D1. Workspace mechanism: persp-mode (spacemacs-layouts)

Enable the =spacemacs-layouts= layer (persp-mode + eyebrowse).  One
perspective per opened pi session.  Rejected: project.el (keys by directory,
cannot express parallel sessions in one dir) and a custom buffer registry
(reimplements persp-mode).

*** D2. Session list UI: unified live/closed picker, framework-agnostic

One list model shared by every session picker (=switch-session=,
=switch-session-in-dir=, =start-new-session=, =close-session=,
=delete-session=):

1. A single builder (=pi-coding-agent//session-targets=) returns
   (LIVE . CLOSED) candidate alists.  LIVE = active pi chat buffers
   (the ground truth, see D3), most recently used first; CLOSED =
   files on disk not loaded by an active buffer.  Each candidate maps
   to a target plist the caller dispatches on (:buffer for live,
   :entry for closed).
2. Rendering is one shared picker (=pi-coding-agent//pick-session=):
   under helm the groups are separate sources ("Live sessions" /
   "Closed sessions" — real section headers); otherwise
   completing-read with non-selectable header rows
   (=────── Live sessions ──────=) between the groups, affixation
   (status glyph ●/○, message count, age), pre-sorted order (live
   first) preserved via display-sort-function identity.  Selecting a
   header row re-prompts.  This works under helm-mode, ivy, vertico
   and the plain minibuffer.
3. Some commands list only one group: close-session offers live
   sessions only (its default is the current perspective's session);
   switch lists both; delete lists both.

(2026 update: previously the switch list derived "opened" from the
persp mapping and had no group boundary; the close/delete picker had
helm sections but no completing-read boundary.  Both are now the
shared model above.)

*** D3. Session identity and perspective mapping

- Registry alist =persp-name -> session-file= (+ =label-locked= flag),
  persisted to the cache directory (=spacemacs-cache-directory=), updated on
  perspective create/rename/destroy, saved on Emacs exit (atomic writes:
  temp file + rename).
- =live= <-> an active pi chat buffer exists (mode
  =pi-coding-agent-chat-mode= with a live process).  Liveness is
  always read from the chat buffers (=active-chat-buffers=), never
  from the registry or the perspective mapping — those can be stale
  (a killed perspective still registered) or miss sessions started
  outside the registry flow.  A perspective with a dead pi process
  lists as closed; switching to it revives the process (the registry
  still maps the perspective).
- After an Emacs restart everything is closed unless auto-resume is enabled
  (see D8).

*** D4. Perspective naming and label sync

- Format: =«title» · «abbrev-path»= (abbreviated full cwd from JSONL header).
- Title: session =/name= (session_info) -> first-message snippet (~40 chars)
  -> =New session= placeholder (before the first prompt).
- Exact collisions (same title + same dir) get a short-uuid suffix.
- Sync policy: auto-sync the title part when the session is renamed — advice
  on =pi-coding-agent-set-session-name= (immediate) plus lazy compare-and-
  rename on the next session-list scan (=/name= slash command path).  A
  perspective renamed by the user (=persp-rename=, SPC l r) sets
  =label-locked= and stops auto-sync.

*** D5. Buffer attribution and common buffers

- persp-mode ='free= attribution (Spacemacs default) attaches every new
  buffer (files, terminals, pi chat/input) to the current perspective.
- Common buffers (=*scratch*=, =*Messages*= by default; defcustom regexp
  list) are injected into every perspective via =persp-created-functions=.
  Injection, not filtering: persp's =persp-common-buffer-filter-functions=
  is an exclusion mechanism (filtered buffers belong to no perspective and
  vanish from the restricted buffer list).  Injected buffers are in all
  perspectives, so they appear in =SPC b b= and are killable without
  foreign-buffer prompts.
- =SPC b B= (non-restricted list) remains the escape hatch.

*** D6. Open/switch state machine

Closed -> open (selecting a closed session):
1. Create the perspective (named per D4) and switch to it.
2. =pi-coding-agent-open-session-file= machinery: setup chat/input buffers,
   start the process, resume the exact session file.
3. Replay the registry's captured buffer specs through persp's load
   dispatch (see D7).
4. Apply the pi window layout, passing the session's own chat/input
   buffers explicitly; focus the pi input buffer.  (The layout fallback
   must not pick the most-recent pi-chat buffer from another
   perspective.)

Live -> switch (selecting a live session):
1. =pi-coding-agent//switch-to-live-buffer=: =persp-switch= to the
   perspective owning the active chat buffer (Spacemacs restores its
   window configuration).  A live buffer outside any perspective falls
   back to opening its file (which reuses the directory's canonical
   chat buffer).

Closed -> switch (reviving a registered perspective): picking a
closed session still routes through =pi-coding-agent//open-or-switch=,
which prefers the perspective the registry (or
=live-session-mappings=) still maps for the file — the session's
perspective exists but its process died.  =switch-to-session= then:
1. =persp-switch= to the perspective (Spacemacs restores its window
   configuration).
2. If the pi process is dead: revive silently (=setup-session= + resume of
   the registry's session file).
3. If the process is alive but its loaded session file (from =get_state=)
   differs from the registry's file — the chat buffer is shared by every
   unnamed session of its directory, so another perspective may have
   resumed a different session into the same process, or a transition was
   skipped while the process was busy — re-resume the registry's file.
4. If the perspective displays a chat buffer of a *different* directory
   (drifted in through the layout's most-recent-buffer fallback), re-assert
   the pi layout with the correct chat/input buffers.

Same-dir collision behavior: opening a session whose directory already has a
live unnamed chat buffer (the package allows one unnamed session per
directory) switches the existing session to the chosen file without asking —
=pi-coding-agent-open-session-file= reuses the dir's canonical chat buffer.

=pi-coding-agent/switch-session= excludes the session of the current
perspective (you are already in it).

*** D7. Buffer save/restore: persp's public dispatch, no duplication

- pi layer registers chat/input handlers only, at the front of persp's
  public defcustoms:
  - =persp-save-buffer-functions=: chat/input buffers ->
    =(def-buffer-pi-chat name dir launch-name session-file)= (dir/launch-name
    from the buffer's session identity, session-file from
    =pi-coding-agent--state=); nil for everything else.
  - =persp-load-buffer-functions=: restore = =pi-coding-agent--setup-session=
    + resume (open-session-file minus window display).
- Registry buffer specs are captured by running persp's save dispatch over
  the perspective's buffers (each owner classifies its own: files/dired by
  persp defaults, terminals by my-persp if present, chat/input by pi) — on
  close-session (before killing), perspective switch-away, and Emacs exit.
- Reopen replays the specs through persp's load dispatch.  No per-type
  classify/restore logic lives in the pi layer.
- No /proc/<pid>/cwd in the pi layer: that is vterm-only logic, owned by
  my-persp.

*** D8. Restart behavior: user's choice, documented

- Auto-resume off (current default): after a restart all sessions are
  closed; the manager list reopens them (registry restores buffers).
- Auto-resume on (=dotspacemacs-auto-resume-layouts t=): persp restores
  perspectives with files (persp defaults), terminals (my-persp), and pi
  sessions (pi layer's chat/input load handler — process restarted, session
  file resumed).  Caveat: N sessions = N pi processes at startup.
- Both modes documented in the README.

*** D9. Close/delete session

Two commands sharing one teardown core (=pi-coding-agent//close-session-
in-persp=): =pi-coding-agent/close-session= (SPC a i d) and
=pi-coding-agent/delete-session= (SPC a i D):

1. Target selection: the pickers list LIVE pi chat buffers (active
   processes) — the perspective containing the chosen buffer is
   resolved only when the selection is acted on.  Close uses the
   current perspective's session without prompting (listing only when
   it has none); delete always prompts and additionally offers closed
   sessions (files on disk not loaded by an active buffer).  Both use
   the unified picker (D2): live first, section boundary, annotated
   candidates.  The picker's default is the current perspective's
   session, resolved from its active chat buffer; when there is no
   active buffer it falls back to the registered session (registry
   entry or chat buffer), so the default still resolves for
   dead-process perspectives.
2. Capture buffer specs (D7) — close only.
3. Kill the pi process (only when the perspective owns its chat
   buffer; a shared same-directory chat buffer is spared), then the
   perspective's buffers (files, terminals, chat/input) — standard
   per-buffer unsaved-change prompts; common buffers and other
   perspectives' buffers never touched.
4. Kill the perspective, then switch to the next perspective (persp
   display order, wrapping) that is associated with a pi session — or
   the next perspective when none is (D9 previously landed in the
   default perspective).
5. Close keeps the registry entry (mapping + captured specs);
   reopening restores the workspace.  Delete additionally deletes
   the session file — moved to the OS trash via the =trash= CLI when
   available, permanent unlink otherwise, mirroring pi's own TUI
   delete (=ctrl+d= in the session tree) — and drops the registry
   entry, so the session vanishes from both lists (the layer's list
   and pi's session manager both scan only =sessions/=).  Deleting a
   closed session (no active buffer) deletes its file and drops any
   registry entry; a perspective still registered for the file is
   torn down like an active session.  Deleting an active session is
   refused while its chat buffer is shared with another perspective
   (the file would move out from under a live process).

*** D10. New-session flow

=pi-coding-agent/start-new-session=:
- Always prompts for the directory; the default follows =pi-coding-agent/
  layout= logic (terminal cwd in terminals, recorded dir in pi buffers,
  buffer dir elsewhere).
- With existing sessions in the chosen directory, offers them through
  the unified picker (D2) — live ● first, then closed ○, with a
  section boundary, live sorted by directory then title, closed
  newest first: picking one opens/switches to it (with its layout),
  typing a fresh name (or picking the
  =✚ New session= candidate and entering one) starts a named session,
  an empty name starts an unnamed session.
- Refuses an unnamed session when the directory already has a live unnamed
  session (package allows one unnamed chat buffer per dir); a name is then
  required for parallelism.  With no session files at all a fresh unnamed
  session starts directly.
- Fresh-session creation is one helper (=pi-coding-agent//start-fresh-
  session=), shared with the bridge tool and the interactive command:
  create the perspective (placeholder label or the name, label-locked),
  =pi-coding-agent--setup-session= (fresh, no resume), applies the layout,
  focuses input, registers the registry entry (session-file resolved
  lazily from chat state).
- =pi-coding-agent/switch-session-in-dir= (SPC a i I) is the scoped
  switch: only the current directory's sessions (recorded dir in pi
  buffers, terminal cwd in terminals, visited file's dir elsewhere),
  same live-first ordering and section boundary (D2), current session
  excluded; switching re-applies the pi window layout.

*** D12. Pi-extension → Emacs bridge (tools that drive the hosting Emacs)

Goal: give sessions started by this Emacs frontend (pi --mode rpc
subprocesses) new LLM-callable tools that act on the hosting Emacs —
first one: open a new session at a tool-specified directory, creating
its perspective and switching to it.

Channel decision: the pi extension shells out to =emacsclient -e=
with a base64-encoded JSON request; Emacs evaluates the layer's
bridge entry (=pi-coding-agent/open-session-at-directory-bridge=) and
returns a JSON string.  emacsclient -e is packet-based, synchronous,
request/response, and needs zero new infrastructure (an Emacs server
is the standard IPC).  Rejected alternatives:

- File mailbox + file-notify polling: works without a server, but
  adds latency, cleanup and a second channel to reason about.
- TCP/HTTP listener in Emacs (make-network-process): port/auth
  management, firewall prompts, an always-on service for a rare need.
- Extension-UI sub-protocol abuse (ctx.ui.*): one-way, no structured
  payloads, blocks the client UI protocols meant for dialogs.
- Upstream pi RPC change (generic extension→host messages): the
  correct long-term fix, but requires pi development; unnecessary for
  a local Emacs host that already owns the process.

Activation decision: the extension lives in the layer directory
(=pi-bridge-extension.ts=) and is wired via =pi-coding-agent-extra-args=
=(-e <path>)= in =packages.el=, so exactly the sessions started by
this Emacs frontend get the tools — no global =~/.pi/agent/
extensions= pollution, no =INSIDE_EMACS= sniffing (Emacs does not set
that variable for subprocesses on this setup, verified).

Instance pinning: an around-advice on =pi-coding-agent--start-process=
exports the Emacs server file to the pi process as =PI_EMACS_SERVER=;
the extension passes it to =emacsclient -s=, so the tool drives
exactly the Emacs instance that owns the session (correct with
daemons or several Emacs running).

Server guarantee: the channel needs a running server.  The layer
defcustom =pi-coding-agent/enable-bridge= (default t) starts one at
layer load when none is running (skips batch and daemon — daemons
always serve).  Independent of =dotspacemacs-enable-server=.

Non-interactive contract: a server eval runs while the pi tool waits
on emacsclient, so bridge entry points must never prompt (no
completing-read, no y-or-n-p).  All failure paths return a JSON error
object instead of signalling.  The bridge entry binds the grammar
prompt state for the duration of the eval: essential grammars degrade
to ='warn= (deferred to an interactive open or M-x
pi-coding-agent-install-grammars) and the optional-grammar question is
skipped — so a bridge call can never block on a minibuffer question.
Interactive session opens keep their normal prompting.  The extension
retries the emacsclient call once (3s backoff) to ride over slow first
setups or a transiently unresponsive server.

Tool: =emacs_new_session= {=directory=, =name=?}.  Mirrors the
=start-new-session= flow non-interactively: create+switch perspective
(«New session · path» or the name, label-locked when named), fresh
=pi-coding-agent--setup-session= (no resume), registry entry, pi
window layout.  Refuses a second unnamed session for a directory that
already runs one (name opens a parallel named session).  Returns
={"ok": true, "persp": ..., "directory": ...}= or
={"ok": false, "error": ...}=; emacsclient prints the Lisp string,
so the extension double-parses (outer Lisp string literal, inner
JSON).

Trust note: any local process able to reach the Emacs server socket
can drive Emacs — the same trust boundary emacsclient already has.
Remote (Tramp) pi sessions are out of scope: the -e path is a local
file.

*** D11. Bindings

| Key       | Command                                | Note                              |
|-----------+----------------------------------------+-----------------------------------|
| SPC a i i | pi-coding-agent/switch-session         | manager list (hub)                |
| SPC a i I | pi-coding-agent/switch-session-in-dir  | switch current dir's sessions     |
| SPC a i n | pi-coding-agent/start-new-session      | new with directory prompt         |
| SPC a i d | pi-coding-agent/close-session          | close current session             |
| SPC a i N | pi-coding-agent-new-session            | reset current (was on =n=)        |
| SPC m p i | pi-coding-agent/switch-session         | mirror in chat/input mode leaders |
| SPC m p I | pi-coding-agent/switch-session-in-dir  | mirror in chat/input mode leaders |

=pi-coding-agent-new-session= (package, reset current) moves from =n= to =N=.

Reset is an in-place package operation: the perspective is kept, the chat
buffer is cleared, and the pi process switches to a new JSONL session
file.  Other package commands switch the session file too: =resume=
(switch_session), =fork= / =fork-at-point= (fork), the direct
=open-session-file= (SPC a i s, switch_session), and =compact= (insurance;
pi rewrites the same file today).  The package never tells the layer
about any of these, so every such command carries =:after= advice
(=pi-coding-agent//sync-registry-after-session-change=, installed by
=pi-coding-agent//install-package-advices=) that issues its own
=get_state= and re-syncs the registry's =:session-file= (preserving
=:label-locked= / =:buffers=) plus the perspective label once the
process has settled on the new file.  RPC ordering guarantees the
=advice= get_state observes the switch (the session-changing RPC is
written first, pi processes RPCs in order); the fork path is advised at
=pi-coding-agent--execute-fork= because the public =fork= command only
sends =get_fork_messages= and the =fork= RPC arrives later, after the
user picks a message.  Without this the stale registry would keep
listing the old file as opened, re-resume it on switch (undoing the
switch), and freeze the label on the old title.  Cancelled/failed/no-op
paths (completing-read cancelled, transition not ready, the layer's own
open flow) and no-registry-entry paths are no-ops.  Commands that do not
change the file need no sync: =reload= re-resumes the same cached file,
=set-session-name= is name-only (label advice), =quit= kills the process
only, and =pi-coding-agent= / =open-named-session= stay registry-less by
design (the session list falls back to scanning perspective buffers).

** Architecture

- =pi-coding-agent= layer (self-contained): registry + orchestration
  (capture/replay through persp's dispatch) + chat/input persp handlers +
  manager UI + close/new commands.  No dependency on my-persp.
- =my-persp= private layer (optional, generic, zero coupling): common-buffer
  injection + terminal save/load for the auto-resume domain.  Listed before
  =pi-coding-agent= in =dotspacemacs-configuration-layers=.
- Registry file: cache directory (runtime state, not versioned dotfiles).

** Fail-open contract

- Registry read failure (missing/corrupt/unknown version): treat as empty;
  sessions still list and open from JSONL; one message logged.
- Per-spec restore failure: condition-case, skip, log to *Messages*;
  never aborts the open.
- Open ordering: perspective -> pi launch + resume (critical) -> layout ->
  buffer restore (best effort, last).  Pi never depends on restore.
- Registry writes are atomic (temp + rename).

** Out of scope (decided)

- Point saving (cursor positions): deferred to a future generic
  Emacs/persp extension; not a pi-layer concern.
- Window-configuration restore for closed sessions.
- Helm-specific session picker (two-source grouping): done — the
  unified picker (D2) renders live/closed as separate helm sources.
- Terminal process state restore (fresh shells in saved cwd only).
- Generic delete-all-buffers command: dropped.

** D13. Unified session listing (2026)

All session-listing commands (=switch-session=, =switch-session-in-dir=,
=start-new-session=, =close-session=, =delete-session=) share one model
(D2):

- Live sessions are always listed by their active pi chat buffers
  (=pi-coding-agent//active-chat-buffers=), most recently used first.
  The old persp-mapping-based =opened= flag could mark a session live
  whose perspective had been killed (stale registry) or whose process
  had died, and could miss sessions started outside the registry
  flow; the buffer scan cannot lie.  A dead-process perspective's
  session now lists as closed; picking it still revives the
  perspective (the registry maps it).
- The builder =pi-coding-agent//session-targets= (dir filter,
  include-closed, exclude-current) feeds every picker; dispatch is
  =pi-coding-agent//open-or-switch-target= (live :buffer ->
  =pi-coding-agent//switch-to-live-buffer=, closed :entry ->
  =pi-coding-agent//open-or-switch=).
- Boundary: separate helm sources, header rows under completing-read
  (re-prompting when a header is selected).  Live always precedes
  closed; within a group the switch list sorts by
  =session-sort-opened= (default =dir-then-name= — directory, then
  title) / =session-sort-closed= (default =chrono= — newest first),
  close/delete keep most-recent-first.
- Fresh sessions without a JSONL file (pi writes it on the first
  response) are now listed as live candidates (label = perspective
  name), selectable like any other live session.

** Implementation notes

- Session-list scan caches per-file metadata keyed by mtime; only changed
  files are re-parsed (hundreds of sessions stay fast).
- New sessions may not have a session file until pi writes one; the registry
  entry stores dir and resolves session-file lazily from chat buffer state.
- Missing-file behavior on registry replay: tune at implementation
  (skip vs. persp's default empty-buffer fallback).
- Label placeholder ("New session") updates to the first-message snippet via
  the lazy scan sync after the first prompt.
